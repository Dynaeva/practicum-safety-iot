# Правила команды

Этот документ фиксирует наши договоренности. Их не меняем без общего голосования в чате.

## 1. Контракт данных

Все контракты описаны в коде: `src/common/contract.py`.  
Изменять формат данных можно **только** через общее голосование в чате и PR в `contract.py`.

Каждый контракт — это «договор» между двумя модулями. Производитель обязан отдать данные строго в этом формате. Потребитель может на них рассчитывать. Валидатор в `contract.py` проверяет это автоматически.

Цепочка контрактов:

```
видео -> [1. Детекция] -> [2. Трекинг] -> [3. События] -> [4. БД/дашборд] -> [5. Конфиг] → весь код
```

### Контракт 1. Детекция

**Кто производит:** Даша (`src/detection/detector.py`, функция `detect`)  
**Кто потребляет:** Ксюша (`src/tracking/tracker.py`, функция `track`)  
**Что передаётся:** список объектов на кадре — `list[dict]`

Поле - Тип - Правило
`cls` - строка - одно из: `"person"`, `"helmet"`, `"vest"`
`bbox` список из 4 чисел - `[x1, y1, x2, y2]` в пикселях, `x1 < x2`, `y1 < y2`, все `>= 0`
`conf` - число уверенность модели, от `0.0` до `1.0`

**Пример правильного объекта:**

```json
{ "cls": "person", "bbox": [120, 45, 300, 400], "conf": 0.91 }
```

**Что нельзя:** добавлять свои поля, менять порядок координат, отдавать `track_id` (это контракт 2).
**Где проверяется:** в конце `detect()`, а также на границе в `main.py`.

### Контракт 2. Трекинг

**Кто производит:** Ксюша (`src/tracking/tracker.py`, функция `track`)  
**Кто потребляет:** Ксюша же (`src/tracking/events.py`) и `main.py`  
**Что передаётся:** те же объекты, что в контракте 1, **плюс** `track_id` у людей.

Поле - Тип - Правило
`cls` - строка - как в контракте 1
`bbox` - список из 4 чисел - как в контракте 1
`conf` - число - как в контракте 1
`track_id` - целое `>= 0` - **только** у `cls == "person"`. У `helmet` и `vest` его быть не должно

**Пример правильного:**

```json
[
  { "cls": "person", "bbox": [120, 45, 300, 400], "conf": 0.91, "track_id": 5 },
  { "cls": "helmet", "bbox": [150, 50, 200, 100], "conf": 0.87 }
]
```

**Почему так:** `track_id` — это «паспорт» человека между кадрами. Он нужен, чтобы понимать «это тот же человек, что и секунду назад». У каски своего ID нет — она привязана к человеку через логику сопоставления.
**Где проверяется:** в конце `track()` и на границе в `main.py`.

### Контракт 3. События

**Кто производит:** Ксюша (`src/tracking/events.py`, функция `build_events`)  
**Кто потребляет:** Полина (`src/db/database.py`, `save_events`) и дашборд  
**Что передаётся:** список событий — `list[dict]`. Событие = «что-то произошло с человеком в кадре N».

Поле - Тип - Правило
`track_id` - целое `>= 0` - к какому человеку относится событие
`event_type` - строка - одно из: `person_appeared`, `person_left`, `helmet_on`, `helmet_off`, `vest_on`, `vest_off`
`frame` - целое `>= 0` - номер кадра, на котором произошло событие
`timestamp` - строка - время в формате ISO 8601: `"2026-11-24T12:34:56"`
`confidence` - число - от `0.0` до `1.0`, уверенность в событии

**Пример правильного события:**

```json
{
  "track_id": 5,
  "event_type": "helmet_off",
  "frame": 420,
  "timestamp": "2026-11-24T12:34:56",
  "confidence": 0.88
}
```

**Почему это важный контракт:** если `event_type` окажется опечаткой, БД запишет событие, но дашборд его не посчитает — и графики молча покажут нули. Валидатор ловит это сразу на выходе из `build_events`.
**Где проверяется:** в конце `build_events`, в начале `save_events` и на границе в `main.py`.

### Контракт 4. Результаты запросов БД

**Кто производит:** Полина (`src/db/database.py`, функции `get_stats`, `get_events_by_hour`)  
**Кто потребляет:** Вика (`src/dashboard/app.py`)  
**Что передаётся:** агрегированные данные для графиков.

**(а) Сводная статистика** — `dict`:

Поле - Тип - Правило
`total_persons` - целое `>= 0` - сколько уникальных людей было
`persons_without_helmet` - целое `>= 0` - сколько людей без каски
`persons_without_vest` - целое `>= 0` - сколько людей без жилета -
`total_events` - целое `>= 0` - сколько всего событий

Пример:

```json
{ "total_persons": 12, "persons_without_helmet": 3, "persons_without_vest": 2, "total_events": 47 }
```

**(б) Динамика по часам** — `list[dict]`:

Поле - Тип - Правило
`hour` - строка - `"2026-11-24 12:00"`
`count` - целое `>= 0` - сколько событий в этот час

Пример:

```json
[
  { "hour": "2026-11-24 12:00", "count": 15 },
  { "hour": "2026-11-24 13:00", "count": 9 }
]
```

**Важное правило:** на пустой БД функции должны возвращать **нули и пустые списки**, а не падать. Дашборд при первом запуске всегда открывается на пустой БД — он не должен падать.

**Где проверяется:** в начале дашборда, перед построением графиков.

### Контракт 5. Конфиг

**Кто производит:** Оля (`configs/config.yaml`)  
**Кто потребляет:** все модули через `src/common/config.py`  
**Что передаётся:** `dict` с настройками.

```yaml
detection:
  model_path: 'yolov8n.pt' # путь к весам YOLO
  conf_threshold: 0.4 # порог уверенности, [0, 1]
  classes: ['person', 'helmet', 'vest']

tracking:
  overlap_threshold: 0.5 # доля пересечения каски и человека, [0, 1]

database:
  path: 'events.db' # путь к файлу SQLite

video:
  output_dir: 'data/output' # куда сохранять результаты
```

**Правила:**

- Все четыре секции обязательны: `detection`, `tracking`, `database`, `video`.
- Все ключи внутри секций обязательны (см. `contract.py`, функцию `validate_config`).
- Значения `conf_threshold` и `overlap_threshold` — числа в `[0, 1]`.
- Классы в `classes` — только из списка `person` / `helmet` / `vest`.

**Почему это контракт:** если в yaml опечатка в имени ключа (`conf_treshold` вместо `conf_threshold`), код упадёт с `KeyError` где-то в глубине. Валидатор конфига ловит это при загрузке — с понятным сообщением «в config[detection] отсутствует ключ conf_threshold».

**Где проверяется:** в `load_config()` сразу после чтения yaml.

### Быстрая шпаргалка: кто что проверяет

Поле - Тип - Правило

1. Детекция - Даша - конец `detect()` + `main.py`
2. Трекинг - Ксюша - конец `track()` + `main.py`
3. События - Ксюша - конец `build_events` + начало `save_events` + `main.py` -
4. БД -> дашборд - Полина - начало `app.py`
5. Конфиг - Оля - `load_config()`

**Правило:** производитель проверяет **свой** выход, потребитель — **свой** вход (для защиты от прямых вызовов в тестах и дашборде). `main.py` проверяет всё на стыках как интегратор.

## 2. Как называть ветки

Работаем только в своих ветках. В `main` напрямую не пушим (только через Pull Request).
Ветки называем по шаблону `тип/название`:

- `<что-то>/detection` - Даша: YOLO и `detect()`
- `<что-то>/tracking` - Ксюша: ByteTrack и логика СИЗ
- `<что-то>/db` - Полина: SQLite и запросы
- `<что-то>/dashboard` - Вика: Streamlit и графики
- `<что-то>/main-skeleton` - Оля: скелет `main.py`

- `feature/<что-то>` - новая функциональность
- `fix/<что-то>` - любые багфиксы
- `docs/<что-то>` - документация
- `test/<что-то>` - тесты

## 3. Владение файлами (один файл — один хозяин)

Чтобы не было конфликтов в Git, каждый редактирует только свои файлы:

- `main.py`, `requirements.txt`, `src/__init__.py` - Оля
- `README.md`, макеты - Вика
- `src/detection/` - Даша
- `src/tracking/` - Ксюша
- `src/db/` - Полина
- `src/dashboard/` - Вика
- `docs/test_plan.md` - Оля и Полина (совместно)

## 4. Базовый Git-флоу (как делать правки)

Перед началом работы над новой задачей:

1. `git checkout main` (переключиться на главную)
2. `git pull origin main` (подтянуть свежие изменения)
3. `git checkout -b feature/имя_ветки` (создать свою ветку)
4. Сделать код -> `git add .` -> `git commit -m "..."` -> `git push origin feature/имя_ветки`
5. На GitHub открыть Pull Request (PR) в `main` и попросить кого-то на ревью.

## 5. Распределение ролей (кратко)

- **Вика:** Менеджер проекта + Дашборд (Streamlit).
- **Оля:** Техлид (сборка `main.py`, интеграция) + Тестирование пайплайна.
- **Полина:** База данных (SQLite) + Тестирование БД и запросов.
- **Ксюша:** Трекинг (ByteTrack) + логика сопоставления СИЗ человеку.
- **Даша:** Детекция (YOLO) + подготовка тестовых видео.
